# 15 分钟视频容量审计

日期：2026-11-11（Asia/Shanghai）。代码快照：本工作区 `outputs/gomotion-mvp/` 当前文件；其他并行任务仍可能继续修改实现。

本轮只读应用代码、查询 Google 官方公开资料，并运行纯本地容量计算。未调用真实模型、未请求本机 / loopback API、未配置密钥、未启动或重启服务。未修改 planner、recovery、脚本拆分行为、应用代码或 TASKS。

## 结论与优先次序

**当前不能宣称支持 15 分钟完整制作。** 整片旁白走一次 TTS，代码拒绝超过 600 秒的单录音；部分入口又限制为 5000 字符。Gemini 模型自身另有输入 / 输出 token 上限，放大字数或把 600 改成 900 无法解决整个链路。

优先实施范围建议如下；均为后续建议，本轮未实施：

1. **提交前统一容量检查。** 把字符、预计时长、所选模型的单请求能力和整片能力放在同一份规则中，创建、旧 `/api/plan` 路径、制作提交、翻译后和统一旁白接口一致验证。超过当前能力时在实际配音 / 检索前明确拒绝，保留完整原稿，避免处理到中途才失败。输入区不应暗示 5000 字符必然可完成。
2. **迁移即将退役的 TTS 接口。** 现用模型最早 2026-11-17 关闭。适配新模型的提示、voice 字段和音频封装后，重新验收原 30 音色 / 15 语言映射与缓存版本。只改模型名称有读出提示或拒绝音频的风险。
3. **增加独立的长旁白音频流程。** 在配音层保存固定声音 / 风格 / 语言和原文顺序，把可恢复的小录音段组装成一条完整音轨与全局时间轴。视觉镜头、检索和已有脚本拆分策略继续保持现有逻辑。
4. **测量并调整长片资源预算。** 再处理每轮 96 MiB 候选读取、兼容缓存、逻辑调用预算、整片审查及截止时间；调整须有真实 15 分钟样片的耗时 / 成本 / 质量记录支持。

第 3 项完成、但素材覆盖 / 整片审片 / 浏览器连续播放未通过时，也只能称长音轨能力已实现。

## 本地可复核计算

调用现有纯函数计算，未发模型请求：

| 输入 / 资源 | 结果 | 解释 |
|---|---:|---|
| 3600 个汉字，无标点，documentary | 预计 900 秒 | 可以落在页面 5000 字符以内，但仍会撞单录音 600 秒限制 |
| 2340 个英文单词 `ocean` | 14039 字符，预计 900 秒 | 明显超过页面 5000 和后台 6000；说明字符上限对不同语言的时长含义不同 |
| 900 秒 / 32 幕 | 28.125 秒 / 幕 | 算术平均，不代表每幕有相应长度的相关动态素材 |
| 900 秒 / 初始 12 幕 | 75 秒 / 幕 | 继续增加原稿长度会放大连续匹配难度 |
| 900 秒审片范围 | 30 块 | 使用当前 `reviewRanges(900)`，并非旧文档的 15 块 |
| 24 kHz、16-bit、单声道 900 秒 PCM | 43200000 字节，约 41.20 MiB | base64 约 57.6 MB，JSON 和解码会另外占内存；96 MiB WAV 缓存最多容纳约两条此长度音轨，还要考虑其他录音 |
| 900 秒、32 幕的 `productionEstimate` | 600–1740 秒 | 只是现有启发式显示值，不是 10–29 分钟完成的实测证据 |

同样按算术估算，浏览器若把整轨解码为 24 kHz float32 单声道，音频样本约 82.4 MiB；若重采样到 48 kHz则约 164.8 MiB。实际设备采样率、缓存副本和峰值内存必须实测，不能只按 WAV 文件大小估算浏览器占用。

96 MiB 分析预算若用于 32 个各不相同候选，平均每份只能约 3 MiB；每幕平均看两份候选则约 1.5 MiB。当前按高清兼容文件计数，这会成为长片的重要约束。该计算不代表实际候选大小或命中率。

## 最小长旁白实现边界

建议把实现限制在音频制作和任务持久化层，先完成可复核的完整音轨，再讨论扩大视觉容量：

- 原文保存一次；每段记录连续字符偏移、原文 hash、模型 / 声音 / 语言 / 风格与处理版本。所有段拼接后的文本必须与完整原稿一致，禁止漏句、重复或改写。
- 以完整段落 / 句子边界建立有界配音段，初始可先验证每段约 2–3 分钟；这是待实测的工程起点。每段遵守实际 token 与输出预算，不能仅按字数判断。
- 固定全片选定声音和稳定风格；生成 / 重试只影响失败段。每段独立缓存和检查点，任务恢复时复用已成功录音，不把“换回同名声音”当作已证明音色绝对一致。
- 逐段验证完整朗读、音轨格式、时长和接缝；只在非语音间隙处理必要的静音 / 响度，禁止用交叠或删词掩盖接缝。将所有有效段封装为一条连续音轨，最终仅添加一次必要尾部帧补时。
- 按实测段长生成全局 offset；已有镜头 / 字幕继续使用一条全局时间轴。对齐和审查采用有界范围与接缝覆盖，避免把更大录音塞进同一个 60 秒对齐等待预算。
- 为任务保存稳定音轨文件或活跃文件引用；缓存清理不得删除仍在制作 / 导出使用的段或整轨。完整音轨和全部视觉覆盖、成片审查都满足后才发布最终视频。
- 中断、限流、鉴权或计费错误停止新增请求，保留段检查点；恢复后不重新消费已完成部分。并发和配额按项目总体控制。

建议先分成两项验收：完整 900 秒音轨，再验证完整 900 秒视频；两项都保留原文、固定声音与可恢复状态。此设计不需要改变本轮禁止修改的脚本 / 检索 / 视觉镜头拆分策略。

## 必须补齐的 15 分钟验收证据

1. 中文和英文各一份约 900 秒真实原稿，记录字符数、输入 tokens、实际音轨时长；证明不是截短脚本、加静音或循环画面补足。
2. 逐段原文 hash / 字符区间、固定声音配置、实测段长和全局边界；逐接缝试听无换人感、重复、缺词、削字和异常停顿。自然度须人工听审。
3. 失败段重试、429 / 每日限额 / 权限错误、显式停止、刷新 / 离开 / 返回和允许的服务重启恢复；报告每次真实模型请求及缓存复用，避免重复生成收费。
4. 全片动态相关画面覆盖率 100%，保持画幅和真实清晰度；缺口补片保留可追溯来源。逐幕实际文件与已审取段长度须覆盖旁白。
5. 900 秒完整 MP4：真实播放 / 暂停 / 拖动 / 跳幕 / 静音、全部边界无闪屏或旁白重启、下载完整解码；浏览器内存和资源释放有记录。
6. 30 个审片范围全部成功，含所有音频段接缝和镜头边界；审片预算不足时保留未完成状态，不能降低覆盖范围来获得通过。
7. 从提交到可播放且审片结束的总耗时，列规划、TTS、检索、媒体、合成、审片、重试和缓存条件；15 分钟片达到用户 2 倍目标需要 ≤1800 秒实测。普通题材和难素材题材分别记录成功率与费用，不能从短片外推。

本轮没有任何真实 900 秒音轨或视频生成结果；当前状态保持为“容量缺口已定位、方案待实施与真实验收”。
